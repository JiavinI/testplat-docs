# Phase 4 路线图与需求核对结论

更新：2026-10-15。来源：10 月 14–15 日用户与主线程的需求核对；本轮用户已同意先做小闭环、参考旧项目后逐步叠加功能。

本文是 Phase 4 起的**需求基线**。与早期需求、架构草图和 4.0 文档冲突时，以本文当前产品要求为准。批次和实现方案是执行拆分，不代表功能已实现。术语见 [CONTEXT.md](../CONTEXT.md)，本批设计见 [4.1 设计稿](phase4.1-design-draft.md)。

## 1. 需求核对结论

| # | 主题 | 当前结论 |
|---|---|---|
| N1 | 定位 | 面向测试人员日常使用的通用接口自动化测试平台；先跑通真实的小功能，再按业务场景叠加能力 |
| N2 | 使用者与部署 | 3–10 人共用一个实例，部署在阿里云内网服务器，浏览器访问 |
| N3 | 用例来源与编辑 | 独立 Git 用例仓库 testplat-assets，远程为自建 GitLab；当前用 IDE 编辑、提交后平台同步。后期支持 Web 修改请求、断言等 case 内容；提交回 Git 还是数据库保存，届时再定。项目由仓库清单派生，一个仓库可含多个项目 |
| N4 | 分支 | 每个仓库跟踪一个固定分支；暂不做分支 / 历史 commit 选择 |
| N5 | 旧项目参考 | testplat-new 只读；参考其 assets/api、assets/scenarios 的接口基础信息、业务步骤、账号切换和数据依赖，按新架构逐步重写。首个闭环沿用 GSB 登录、查余额、搜商品，不整体迁移旧资产或旧 DSL |
| N6 | 环境 | 每个项目单独维护环境，运行时选择。环境列表、服务地址、超时和配置变量在 Web 维护；新建环境不以 Git 中存在同名文件为前提 |
| N7 | 登录方式与凭据 | 登录流程放 Git，包含登录接口、字段映射、结果提取与注入方式。测试账号、密码等日常配置在 Web 维护，保存在平台数据库；真实秘密不进 Git。服务器环境变量保留给平台自身配置及加密主密钥 |
| N8 | 测试账号 | 每项目可维护多个业务角色的账号；按“项目 + 环境 + 账号名”定位，不跨项目共用。case 引用账号名；角色是被测业务角色，不是平台权限角色。登录缓存按项目、环境、账号及材料指纹区分 |
| N9 | 隔离与排队 | 同项目、同环境的执行最终串行排队，不同项目 / 环境可并行；平台用户之间可共用该项目里的测试账号。排队未交付前不能宣称业务数据已隔离 |
| N10 | 平台登录 | 自主注册（用户名 + 密码）与登录，用来记录操作人。现阶段所有登录用户可维护配置、账号和运行；不引入超管分级或复杂权限。平台用户密码与被测系统测试密码分别管理 |
| N11 | 结果分享 | 保留公开分享链接需求（无平台账号也能打开，仅内网可达），暂不导出；优先让位于配置闭环 |
| N12 | 脱敏 | 内部使用，调试从简；期望的全局开关默认关闭、日志始终遮挡。现有 Engine 脱敏能力保留，开关单独排期；配置管理不顺带改变所有执行结果的脱敏行为。测试账号页面可查看、编辑凭据；平台用户登录密码只保存哈希、不可查看 |
| N13 | 执行与场景 | 支持单接口与串行 API case，展示每步请求 / 响应 / 结果。逐步完善按步骤引用账号、跨步骤传值、跨系统场景和断言；接口定义复用，重复流程出现后再抽 flow |
| N14 | 优先级 | Web 配置与 GSB 冒烟闭环 → 多账号 / 跨系统场景和排队 → 后续 Web 编辑 case；套件和定时在结果管理之后，UI 自动化再往后 |
| N15 | 数据库 | 当前开发数据允许删除重建，不要求现在引入迁移工具。不能由程序自动删库；正式给团队使用后重新确定备份与表结构升级方式，不能继续默认可清空 |
| N16 | 配置生效与追溯 | 保存后供下一次运行使用；一次运行固定资产 commit 和启动时的配置。执行记录应带环境、操作人、配置版本、所用账号名等，历史记录不随配置编辑而改写 |

## 2. 数据归属

| 内容 | 维护位置 |
|---|---|
| 项目清单、接口定义、case、登录流程 | Git 资产仓库；case Web 编辑是后期能力 |
| 项目环境、业务 / 登录服务地址、超时、配置变量、测试账号及凭据 | Web → Control 数据库 |
| 平台用户、操作记录、执行记录 | Control 数据库 |
| Git 访问凭据、平台加密主密钥等部署配置 | 服务器 |

一个业务项目可包含 GSB、代发后台等多个被测系统，分别使用逻辑 host 和各自账号。旧项目 GO2 / e3e3 就是这种组织方式，不能据 GSB 首批示例推断“项目必须等于一个被测系统”。

Git config/envs/*.yaml 后续定位为初始化模板，不应在同步时覆盖 Web 配置。**是否首次同步自动导入仍未单独裁决**；4.1 设计先以 Web 创建环境为闭环，不以自动导入为前置依赖。

## 3. 批次与小步验收

| 批次 | 内容 | 状态 |
|---|---|---|
| 4.0 | Git 同步、只读 commit 快照、资产浏览与 GSB 冒烟；执行记录保存 env、commit，operator 可空 | 已有实现；本轮未重新验收发布状态 |
| 4.1a | 自主注册 / 登录、操作人；Web 维护项目内环境、host、变量和多账号；数据库配置接入现有 GSB 冒烟；改配置后重跑 | 设计稿就绪，待实现 |
| 4.1b | case 步骤按账号名选身份；单接口可选账号；先用同一接口的两个账号验证，再接实际跨系统场景 | 设计方向就绪；需 Engine 契约增量与兼容测试 |
| 4.2 | 最小跨系统 API 场景与同项目 + 同环境排队；为真实场景逐项补齐数据处理和断言能力 | 后续设计；复用已支持的基础跨步骤引用 |
| 4.3 | Web 编辑请求 / 断言等 case 内容；确定保存与 Git 同步规则 | 后续设计 |
| 后续 | 完善结果管理、分享链接和脱敏开关 → 套件 / 定时 → 账号管理 / 权限 → UI 自动化 | 具体顺序按使用反馈调整 |

4.1a 与 4.1b 分开交付；每一段完成后即可展示、验证。分享 / 脱敏仍是需求，只是移出 4.1 的首个小闭环。

## 4. 对已发布设计的影响

- 4.0 的 Git 同步、资产快照和 commit 追溯继续使用；“配置全在 Git / 服务器”“永远不做 Web 编辑 case”仅代表当时范围。
- 4.1a 在 Control 构造 environment 和 AuthTable，Engine 继续执行登录与 HTTP；不能让 Engine 读取平台数据库或让 Control 另写 case 执行器。
- 4.1b 才增量扩展步骤选择账号的契约。现有严格 schema 不接受 account，不能提前写进资产并假设生效。
- Engine 已支持 output alias 和后续步骤 ${alias.body.field} 引用；尚未支持旧项目整套 JSONPath、flow、循环和断言 DSL，逐项验证后演进。
- 3.3d 缓存已有配置 / 凭据指纹；编辑账号后新运行不能命中旧材料，需验收。后端日志始终遮挡，不因简化权限而打印凭据。
- 历史设计与当前运行能力分开：以本基线描述产品要求，以 Engine 代码和兼容文档确认已实现能力。
