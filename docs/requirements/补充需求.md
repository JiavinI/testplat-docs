## 历史补充需求（2026-10-09，优先级与语法以现行基线覆盖）

### 1. 脱敏控制 (P0)

**需求描述**:
- 测试报告中的请求/响应展示需要支持脱敏开关控制
- 不是全局脱敏,而是可选的开关
- 用户可以在查看结果时选择是否显示敏感信息

**设计约束**:
- 脱敏逻辑不能硬编码,必须可配置
- 支持字段级脱敏规则 (如 password/token/phone)
- 不同项目可能有不同的脱敏规则

**实现要点**:
```python
# 配置文件定义脱敏规则
redaction_rules:
  - field: password
    type: mask
    pattern: "***"
  - field: token
    type: first_last
    show_prefix: 4
    show_suffix: 4
  - field: phone
    type: regex
    pattern: "(\\d{3})\\d{4}(\\d{4})"
    replacement: "$1****$2"

# 前端展示时支持切换
<ResultViewer 
  result={executionResult}
  showSensitive={false}  // 用户可切换
/>
```

### 2. API + UI 混合测试 (P0)

**需求描述**:
- testplat-new 已经支持在一个 case 中混合 API 步骤和 UI 步骤
- 新平台必须保留这个能力,且设计上要有扩展性

**参考 case**: `/Users/jiavin/Developer/products/testplat-new/assets/scenarios/go2/order/full_pay/items_search_visible.case.yaml`

**设计约束**:
- ❌ 禁止为实现功能而打补丁
- ✅ 必须考虑扩展性和可维护性
- ✅ 步骤类型应该是插件化的 (api/ui/db/redis/custom)

**实现要点**:
```yaml
# case 示例: 混合 API 和 UI 步骤
steps:
  - name: API 创建订单
    kind: api
    use: api.order.create
    with:
      items: "${params.items}"
    ->: order
  
  - name: UI 搜索订单
    kind: ui
    page: order_list
    actions:
      - type: fill
        selector: "#order_no"
        value: "${order.order_no}"
      - type: click
        selector: "button[type=submit]"
  
  - name: UI 验证订单可见
    kind: ui
    page: order_list
    assert:
      - selector: "tr[data-order-id='${order.order_no}']"
        visible: true
```

**架构设计要求**:
```python
# 步骤执行器必须是策略模式
class StepExecutor(ABC):
    @abstractmethod
    def execute(self, step: Step, context: Context) -> StepResult:
        pass

class ApiStepExecutor(StepExecutor):
    def execute(self, step: Step, context: Context) -> StepResult:
        # API 执行逻辑
        pass

class UiStepExecutor(StepExecutor):
    def execute(self, step: Step, context: Context) -> StepResult:
        # UI 执行逻辑 (Playwright)
        pass

# 执行器注册表
class StepExecutorRegistry:
    def register(self, kind: str, executor: StepExecutor):
        self._executors[kind] = executor
    
    def get(self, kind: str) -> StepExecutor:
        return self._executors[kind]

# 主执行循环
for step in case.steps:
    executor = registry.get(step.kind)
    result = executor.execute(step, context)
```

## 设计原则 (强制约束)

### 1. 禁止打补丁
- ❌ 不允许为了实现某个功能而在核心代码中硬编码特例
- ✅ 所有扩展点必须通过插件机制实现

### 2. 扩展性优先
- 步骤类型必须是可注册的 (api/ui/db/redis/custom)
- 鉴权策略必须是可注册的 (bearer/form/oauth2/custom)
- 脱敏规则必须是可配置的

### 3. 可维护性优先
- 清晰的分层架构 (domain/engine/application/adapters)
- 单一职责原则
- 依赖注入而非硬编码依赖

## 技术债务风险

### 风险: UI 自动化集成复杂度

**背景**: Playwright 集成需要:
- 浏览器驱动管理
- 页面对象模型 (Page Object)
- 元素定位策略
- 截图和错误恢复

**应对**:
1. 复用 testplat-new 的 `plugins/playwright_driver.py`
2. 抽象出 `BrowserProvider` 接口
3. UI 步骤执行器独立模块,不侵入核心引擎

### 风险: API + UI 混合的状态管理

**背景**: API 步骤生成的数据需要传递给 UI 步骤

**应对**:
- 统一的 `Context` 对象管理变量
- 变量渲染引擎支持 `${order.order_no}` 语法
- 确保 API 和 UI 步骤都能读写同一个 Context

## 参考实现

testplat-new 中的成功经验:

1. **步骤类型识别**: `step.kind` 字段区分 api/ui/db 等
2. **Page Object**: `assets/pages/*.page.yaml` 定义页面元素
3. **UI 步骤**: 支持 fill/click/navigate/wait/screenshot 等操作
4. **混合执行**: `engine/executor.py` 统一调度不同类型步骤
