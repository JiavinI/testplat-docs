## 项目概述

### 项目名称
testplat - 通用接口自动化测试平台

### 项目定位
构建一个**通用的、可跨公司复用的接口自动化测试平台**,具备以下核心特性:
- **通用性**: 不依赖特定业务/公司的硬编码逻辑
- **可移植性**: 换公司后只需调整配置文件,无需修改平台代码
- **渐进式**: 先实现最小可用 MVP,在使用中逐步完善功能

### 参考基线
基于现有的 `/Users/jiavin/Developer/products/testplat-new` 项目,该项目已验证的成功经验包括:
- 六边形架构设计 (domain/engine/application/adapters 分层)
- YAML DSL 测试资产组织方式 (api/scenarios/suites)
- 三层配置合并机制 (_global.yaml < {env}.yaml < {env}/{project}.yaml)
- 鉴权策略插件化设计

## 一、架构设计

### 1.1 架构拆分原则

**双仓库架构**:

```
testplat-control (控制仓库)
├── Web UI (React + Ant Design)
├── FastAPI 后端
├── 项目配置管理
├── 任务调度
└── 结果归档

testplat-engine (执行引擎)
├── 复用 testplat-new 核心模块
├── YAML DSL 执行
├── HTTP 客户端
├── 断言引擎
└── 鉴权插件
```

**职责边界**:

| 模块 | 职责 | 不负责 |
|------|------|--------|
| testplat-control | Web UI、项目管理、任务调度、结果展示 | 测试执行、HTTP 请求、断言判定 |
| testplat-engine | 测试执行、HTTP 客户端、断言引擎、鉴权 | Web UI、项目配置管理、结果持久化 |

### 1.2 技术栈选型

**后端**:
- FastAPI (Python 3.12+)
- SQLite (项目配置和执行记录)
- httpx (HTTP 客户端)
- Pydantic (数据校验)

**前端**:
- React 18 + TypeScript
- Ant Design 5
- React Query (数据获取)
- Monaco Editor (YAML 编辑器)

**通信**:
- REST API (主要)
- WebSocket (实时进度推送)

## 二、MVP 核心功能

### 2.1 项目与用例仓库 (P0)（2026-10-14 变更）

#### 功能描述
- 接口、case、登录流程存放在独立 Git 资产仓库；环境、地址、变量和测试账号通过 Web 维护，保存在 Control 数据库
- 仓库由管理员在服务端配置（`TESTPLAT_REPOS_FILE`）登记，Web 上**不能**新建/编辑/删除项目或仓库
- 项目由仓库根目录清单 `testplat.yaml` 派生；平台多人共用，可“同步”拉取最新提交
- 每次执行固定在某个 commit 的只读快照上；同步不影响正在运行的执行
- 环境在各项目内独立维护，运行时选择；Git 是否首次自动导入环境模板另定，不覆盖 Web 已维护的数据
- 秘密不进仓库；测试凭据由 Web 维护并加密存数据库，登录流程只引用所需凭据字段

#### 数据模型
```python
class Repo:
    key: str
    branch: str
    current_sha: str
    last_sync_at: datetime
    last_sync_result: str  # ok / network / auth / invalid_manifest / timeout

class Project:
    id: str            # "{repo}/{project}"
    repo: str
    name: str
    envs: list[str]
    default_env: str | None
    archived: bool
```

#### 界面设计
- 项目列表页: 按仓库分组展示项目（只读），显示短 SHA、最近同步时间，“同步”按钮
- 项目详情页: 环境下拉 + 左侧资产树 + 右侧内容区

### 2.2 资产管理 (P0)

#### 资产类型
1. **API 契约** (`assets/api/*.yaml`)
   - 定义接口的 URL、method、请求体结构、成功判定条件
   - 可直接运行单接口调用

2. **测试场景** (`assets/scenarios/*.case.yaml`)
   - 多步骤编排的测试用例
   - 支持变量渲染、断言、流程复用

3. **测试套件** (`assets/suites/*.suite.yaml`) - 暂不实现
   - 批量执行场景的选择集

#### 界面设计
- 左侧树形导航: 展示项目下的所有资产
- 右侧内容区: 显示选中资产的元信息和执行按钮

## 三、配置管理模块 (P0)

### 3.1 数据归属（2026-10-15 修订）

| 内容 | 维护位置 |
|---|---|
| 项目清单、接口、case、登录流程 | Git 资产仓库 |
| 项目内环境、服务地址、超时、业务参数默认值 | Web → Control 数据库 |
| 项目 + 环境 + 账号名对应的测试凭据 | Web → 加密数据库字段 |
| 平台用户、操作人与执行记录 | Control 数据库 |
| 平台主密钥、Git 访问凭据 | 服务器部署配置 |

### 3.2 生效规则

- 运行时选择该项目的环境；一个环境可配置多个被测系统的逻辑 host。
- 下一次运行使用保存成功的配置；已开始的运行固定启动时的 commit 和配置。
- 业务参数按顶级键浅层覆盖：运行请求 > 平台环境默认值 > case 默认值；不把秘密作为业务参数传递。
- 登录缓存按项目、环境、账号及材料指纹区分；改凭据后新运行不能复用旧材料。

### 3.3 Web 配置界面

先实现环境与测试账号表单。账号包括账号名、展示名、业务角色、Git 登录流程和按环境区分的凭据；可查看 / 编辑密码。所有登录用户均可维护，不做复杂权限和超管分级；平台登录密码不可查看。

### 3.4 Git 同步和未来编辑

同步更新接口、case 和登录流程的 commit，不覆盖数据库环境与账号。当前 case 经 IDE / Git 维护，后期支持 Web 修改请求、断言等内容；提交回 Git 还是数据库保存，后续设计再定。旧项目只读，参考 api / scenarios，按小功能渐进重写。

## 四、鉴权架构 (P0)

### 4.1 设计目标

- **通用性**: 覆盖常见鉴权方式 (Bearer Token/HTTP Form/Cookie Session/OAuth2)
- **可扩展性**: 新增鉴权策略无需修改引擎核心代码
- **配置驱动**: 用例只声明"谁在操作",配置文件决定"怎么登录"

### 4.2 账号与登录方式分开

case 选择账号名 → 当前项目 + 所选环境定位 Web 账号 → 该账号引用 Git 登录流程 → Control 构造 AuthTable → Engine 执行登录并注入凭据。

4.1a 先让当前 API 的 auth 身份名对应同名账号；4.1b 再扩展步骤 account 选择。早期 as / profile 路由示例不是新 Engine 的现行 DSL。

### 4.3 内置策略

1. **bearer_token**: 直接使用预置 Token
2. **http_form**: 表单登录 (用户名密码 POST)
3. **cookie_session**: Cookie 会话登录
4. **oauth2**: OAuth2 授权码模式 (扩展示例)

### 4.4 策略插件接口

```python
class LoginStrategy(ABC):
    @property
    @abstractmethod
    def name(self) -> str:
        pass
    
    @abstractmethod
    def login(self, ctx: AuthContext, http_client: Any) -> AuthResult:
        pass
    
    def validate_params(self, params: Dict[str, Any]) -> None:
        pass
```

### 4.5 缓存与自愈

- Token 缓存 (避免频繁登录)
- 401 自动重登并重试请求
- 当前 Engine 缓存键：cache_scope + identity + 材料指纹；Control scope 使用 repo:project:env，identity 对应账号名

## 八、验收标准

MVP 交付时必须满足:

1. ✅ 服务端登记一个 Git 用例仓库后，Web 界面列出其中的项目；仓库新提交后点“同步”即可看到（2026-10-14 变更，原为“Web 创建项目”）
2. ✅ 可以在 Web 界面看到该项目下的所有 API 和 Case 资产，并选择运行环境
3. ✅ 可以点击某个 API,填写参数后运行,并看到请求/响应
4. ✅ 可以点击某个 Case,运行后看到步骤级结果
5. ✅ 执行记录保存环境、commit SHA、操作人和配置版本，配置编辑不改写历史
6. ✅ **换一台机器,只需修改服务端仓库配置,即可正常使用** ← 通用性核心指标

- 性能测试模式 (压测)
- CI/CD 深度集成

## 十、技术债务与风险

### 10.1 复杂度控制

**风险**: testplat-new 的鉴权体系非常复杂 (多租户、多策略)

**应对**: MVP 仅支持最常见的 3 种鉴权方式,后续按需扩展

### 10.2 跨平台兼容性

**风险**: 文件路径在 Windows/Linux/Mac 表现不同

**应对**: 统一使用 `pathlib.Path`,强制使用绝对路径

### 10.3 并发执行

**风险**: 多用户同时运行可能冲突

**应对**: MVP 阶段串行执行,后续版本再加任务队列

## 十一、与 testplat-new 的差异对比

| 维度 | testplat-new | testplat (通用版) |
|------|--------------|-------------------|
| 定位 | 特定公司的业务测试平台 | 通用的开源测试框架 |
| 架构 | 单体仓库 (CLI) | 双仓库 (control + engine) |
| 鉴权 | 复杂多租户 + 多策略 | 简化版 + 插件扩展 |
| UI | 仅 CLI + HTML 报告 | Web 管理界面 + CLI |
| 配置管理 | 文件编辑 | Web 界面 + 加密存储 |
| 项目绑定 | 硬编码 GSB/GO2/e3e3 | 配置文件驱动 |
| 数据库 | SQLAlchemy 连接池 | MVP 暂不支持 |
| UI 自动化 | Playwright 集成 | MVP 暂不支持 |
| 部署方式 | 本地 CLI | Web 服务 + API |

---

## 十二、核心设计原则

1. **配置驱动,而非代码驱动**: 业务逻辑通过配置文件控制
2. **插件化扩展**: 新增鉴权策略、数据源等无需修改核心代码
3. **关注点分离**: control 负责编排,engine 负责执行
4. **安全第一**: 敏感配置加密存储,鉴权 Token 缓存
5. **用户友好**: Web 界面降低使用门槛,实时反馈执行进度
