## 执行摘要

通过系统的 grill 流程,确认了 testplat 通用测试平台的所有核心架构决策。本报告记录了每个决策的背景、选项、用户反馈和最终结论。

3. **设计原则**: 确立了"禁止打补丁"的强制约束,所有扩展通过插件机制

5. **渐进式演进**: 从简单的 MVP (串行执行) 到完整系统 (并发 + 趋势分析)

## Grill 决策详情

### Q0 - 补充需求确认
**背景**: grill 开始前,用户补充了两个关键需求

**关键洞察**:
- "脱敏做成开关试的" → 配置驱动的脱敏规则 (全局+项目级)
- "对应参考 case: items_search_visible.case.yaml" → API + UI 混合是核心功能
- "禁止是为了实现功能而打补丁" → 强制扩展性设计

**决策**: ✅ MVP 支持脱敏开关和 API + UI 混合 (P0)

### Q1 - 目标用户与团队规模
**问题**: 平台的使用者是谁?团队规模多大?

**用户确认**: 3-10 人团队,包括测试工程师、测试负责人和偶尔的开发人员

**决策**: ✅ MVP 不需要复杂的权限控制,只记录操作人

### Q2 - 多用户协作与权限控制
**问题**: 3-10 人团队的权限控制策略?

**方案对比**:
| 方案 | 复杂度 | 是否采用 |
|------|--------|---------|
| 简单方案 (只记录) | 低 | ✅ MVP |
| 中等方案 (项目级权限) | 中 | Phase 2 |
| 复杂方案 (RBAC) | 高 | 不考虑 |

**决策**: ✅ 采用简单方案 (MVP)

### Q3 - 部署方式
**问题**: 平台的部署方式?

**方案确认**: 
- MVP: 本地部署 (uvicorn 启动)
- 同时提供: docker-compose 一键启动

**决策**: ✅ 混合方案

### Q4 - 浏览器生命周期管理
**问题**: API + UI 混合执行时,浏览器如何管理?

**关键洞察**:
- "部署到服务器中的话有头也不能使用" → 需要智能判断 headless 模式

**方案确认**:
- 浏览器模式: 独立会话 / 复用 (可配置切换)
- Headless 模式: 自动判断 (服务器强制无头)

**决策**: ✅ 两种模式支持 + 环境自适应

### Q5 - 脱敏规则配置粒度
**问题**: 脱敏规则在哪个层级配置?

**方案确认**:
- 全局规则: 通用敏感字段 (password/token/phone)
- 项目规则: 项目特殊字段补充

**决策**: ✅ 全局+项目级补充规则

### Q6 - Page Object 与测试数据管理
**问题**: 如何组织 Page Object 和测试数据?

**关键洞察**:
- "可以参考不一定是复制过来,需要根据平台来设计" → 要现代化设计
- 需要考虑场景运行中的变量维护

**改进设计**:
- Page Object: 支持继承机制,YAML 定义
- 元素选择器: 支持 Playwright role-based selector
- 测试数据: 支持多文件合并,profile 变体

**决策**: ✅ 现代化设计,支持继承和组合

### Q7 - 步骤类型扩展机制
**问题**: 除了 API 和 UI,未来还有哪些步骤类型?

**方案确认**:
- MVP: api + ui 内置
- 未来: db / redis / wait / custom (通过插件机制)

**设计**: 步骤执行器注册表 (完全插件化)

**决策**: ✅ 插件化架构,禁止硬编码

### Q8 - 并发执行与资源隔离
**问题**: 多用户并发执行时如何避免冲突?

**方案对比**:
| 阶段 | 方案 | 特点 |
|------|------|------|
| MVP | 串行执行 (全局锁) | 简单,无冲突 |
| Phase 2 | 任务队列 | 不阻塞用户,按序执行 |
| Phase 3 | 完全并发 | 复杂,按需实现 |

**决策**: ✅ 渐进式方案 (MVP 串行 → Phase 2 队列)

### Q9 - 失败重试与错误恢复
**问题**: 失败重试策略?自动重试还是手动?

**关键洞察**:
- "先不要自动重试" → 用户重新运行即可
- 保留 wait_until 机制 (步骤内轮询)

**决策**: ✅ MVP 无自动重试,保留 wait_until

### Q10 - 测试报告的保存与查询
**问题**: 报告如何保存?查询需求?清理策略?

**关键洞察**:
- "后期会在专门的页面展示运行趋势" → 需要保留历史数据支持分析

**决策**: 
- ✅ MVP: 保存所有结果,无自动清理
- ✅ Phase 2: 趋势分析 + 自动清理策略

### Q11 - 资产文件的管理方式
**问题**: 资产文件如何编辑?本地编辑后如何同步?

**关键澄清**:
- "是在本地编辑后上传到服务器吗?" → 确认工作流

**工作流确认**:
1. 本地 IDE 编辑 YAML
2. 通过 Web UI 或 CLI 批量上传
3. 刷新 Web 页面查看最新资产

**决策**: ✅ 本地编辑 + 上传模式 (MVP)

> **2026-10-14 修订**：改为“本地 IDE 编辑 → Git 提交到独立用例仓库 `testplat-assets` → 平台点‘同步’（git fetch）→ 刷新查看”。不做上传；每次执行固定在一个 commit 快照上，执行记录保存 commit SHA。

### Q12 - 环境隔离与多项目支持
**问题**: 多项目、多环境如何隔离?

**隔离机制确认**:
- 项目隔离: (project_id, env) 二元组
- 用户隔离: 每次执行独立 Context
- 配置隔离: 三层合并 (_global < env < project)

**决策**: ✅ 严格隔离 (三维隔离: project+env+user)
